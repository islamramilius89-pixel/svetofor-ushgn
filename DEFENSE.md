# Защита проекта «Светофор УШГН»

Репозиторий: https://github.com/islamramilius89-pixel/svetofor-ushgn

## 1. Коротко (вступление, ~1 минута)

«Светофор УШГН» — веб-приложение для мониторинга нефтяных скважин. Система «Светофор»
анализирует ток двигателя насоса и подсвечивает скважины: 🟢 норма, 🟡 отклонение,
🔴 срочно проверить. По проблемным скважинам инженеры создают заявки и ведут их на доске
в стиле Jira. Администратор управляет скважинами, заявками и сообщениями в админ-панели.

**Соответствие заданию хакатона:**

| Требование | Как выполнено |
|---|---|
| Полноценное приложение с несколькими страницами | 8 разделов: главная, список скважин, карточка скважины, доска заявок, заявка, контакты, результаты, админ-панель |
| Взаимодействие с компонентами | фильтры и поиск, избранное, перетаскивание карточек, модальные окна, комментарии, формы с проверкой |
| Бэкенд: FastAPI / NestJS | **NestJS 12** |
| Фронтенд: React / Next | **Next.js 16 + React 19** |
| Zustand + TanStack Query | **Zustand** — избранное и настройки интерфейса; **TanStack Query** — данные сервера |
| Zod | проверка форм, ответов API и параметров адреса — на фронтенде **и** на бэкенде |
| База данных | **SQLite** через **Prisma 7**: 6 таблиц, миграции, начальные данные |
| Доп. баллы: админ-панель | вход по паролю, JWT в httpOnly-cookie, управление скважинами, заявками и сообщениями |

## 2. Как устроено приложение целиком

```
Браузер ──► Next.js (3000) ──/api/*──► NestJS (4000) ──► Prisma ──► SQLite (файл dev.db)
```

1. Браузер открывает страницу на Next.js.
2. Данные страница берёт из API по адресу `/api/...` на том же домене.
3. Next.js пересылает эти запросы на NestJS (настройка `rewrites` в `next.config.ts`).
4. NestJS проверяет права и данные, обращается к базе через Prisma и отвечает JSON.

**Почему запросы идут через Next.js, а не напрямую на порт 4000?** Для браузера фронтенд и API
находятся на одном адресе. Поэтому cookie администратора отправляется автоматически, а CORS
настраивать не нужно.

## 3. Бэкенд (NestJS)

### Модули

| Модуль | Что делает |
|---|---|
| `PrismaModule` | одно подключение к базе на всё приложение |
| `AuthModule` | вход, выход, JWT, `AdminGuard` |
| `WellsModule` | скважины и НГДУ |
| `TicketsModule` | заявки и комментарии |
| `MessagesModule` | форма обратной связи |
| `StatsModule` | сводка по статусам |

В каждом модуле три части:
- **controller** принимает HTTP-запрос и отдаёт ответ;
- **service** содержит логику и работу с базой;
- **schemas** описывают правила проверки входящих данных (Zod).

```ts
@Post('wells')
@UseGuards(AdminGuard)                                           // только администратор
create(@Body(new ZodValidationPipe(wellInputSchema)) body: WellInput) {   // проверка данных
  return this.wells.create(body)                                 // логика — в сервисе
}
```

### База данных (Prisma + SQLite)

Схема описана в `backend/prisma/schema.prisma`:

```
Ngdu 1 ──< Well 1 ──< Ticket 1 ──< Comment
Message (сообщения с формы)      Admin (администраторы)
```

- `Well.status` — перечисление `GREEN | YELLOW | RED`.
- При удалении скважины удаляются её заявки, а при удалении заявки — её комментарии (`onDelete: Cascade`).
- Изменения схемы оформляются **миграциями** (`prisma/migrations`), поэтому базу можно воспроизвести с нуля.
- `seed.ts` заполняет базу одинаковыми тестовыми данными: генератор случайных чисел детерминированный.

**Почему SQLite?** База — это один файл, устанавливать ничего не нужно, проект запускается одной
командой. Prisma скрывает различия между базами, поэтому переход на PostgreSQL — это смена
провайдера в схеме.

### Главные правила предметной области

`wells/well-status.ts` — статус рассчитывается из отклонения тока:

```ts
export function statusFromDeviation(deviation: number): WellStatus {
  if (deviation >= 25) return 'RED'
  if (deviation >= 10) return 'YELLOW'
  return 'GREEN'
}
```

Статус нельзя выставить вручную: администратор меняет отклонение, а статус пересчитывается сам.

`tickets/ticket-rules.ts` — что происходит при смене статуса заявки:
- перевели в «Проверено» → фиксируется дата закрытия, у скважины обновляется **дата последней проверки**;
- вернули из «Проверено» → дата закрытия сбрасывается.

Чтение текущего статуса и запись выполняются в одной **транзакции**, чтобы между ними ничего не изменилось.

### Проверка данных и ошибки

- `ZodValidationPipe` проверяет тело запроса, query-параметры и id. В контроллер попадают только
  проверенные данные.
- `HttpErrorFilter` приводит все ошибки к одному формату:
  `{ "error": "Скважина с таким номером уже есть", "fieldErrors": { "number": "Этот номер уже занят" } }`.
- Ошибки базы переводятся в понятные ответы: повтор номера → **409**, нет записи → **404**,
  несуществующее НГДУ → **400**.
- Сообщения Zod переведены на русский (`z.config(z.locales.ru())`).

### Безопасность

| Мера | Зачем |
|---|---|
| Пароль хранится как хеш **scrypt** с солью | даже при утечке базы пароль не узнать |
| Сравнение хеша за постоянное время (`timingSafeEqual`) | по скорости ответа нельзя подобрать пароль |
| JWT в **httpOnly-cookie** | JavaScript на странице не может прочитать токен, значит его не украсть через XSS |
| `sameSite: 'lax'` | cookie не уходит с запросами, которые инициировал чужой сайт |
| `AdminGuard` на каждом закрытом методе | права проверяет сервер, обойти интерфейс бесполезно |
| 5 неудачных попыток → блокировка на 15 минут | защита от подбора пароля |
| Одинаковая ошибка «Неверный логин или пароль» | нельзя узнать, существует ли логин |
| Список сообщений закрыт | email отправителей видит только администратор |
| В production без `JWT_SECRET` сервер не запустится | нельзя случайно оставить тестовый секрет |

### Тесты (26 штук, Vitest)

- **Модульные (18):** правило статуса, переходы заявок, хеширование пароля, блокировка входа, проверка данных.
- **API (8):** без входа нельзя читать сообщения и удалять скважины, поддельный токен не принимается,
  неверные данные дают 400 с ошибками по полям и ничего не пишут в базу. В этих тестах база
  подменена заглушкой, проверяется именно HTTP-слой.

## 4. Фронтенд (Next.js + React)

### Слои (скилл `next-frontend-architecture`)

```
app → components → flows → interactions → use-cases → infrastructure → API
```

| Слой | Пример в проекте |
|---|---|
| `app/` — маршруты | `wells/page.tsx` читает фильтры из адреса на сервере |
| `components/` — экраны | `BoardScreen`, `TicketCard`, `WellsScreen` |
| `flows/` — сценарии экранов | `useBoardFlow`: колонки, перетаскивание, фильтры, окно создания |
| `interactions/` — TanStack Query | `useUpdateTicketMutation` с оптимистичным обновлением |
| `use-cases/` — действия | `submitForm`: проверка → запрос → ошибки по полям |
| `infrastructure/` — запросы | `http-client.ts` (браузер), `server-api.ts` (сервер, пересылает cookie) |
| `domain/` — правила | схемы Zod, `statusFromDeviation`, `groupTicketsByStatus`, разбор фильтров |
| `stores/` — Zustand | `favorites-store`, `preferences-store` |

### Где хранится какое состояние (частый вопрос)

| Состояние | Где | Почему |
|---|---|---|
| Фильтры скважин и доски | **адрес страницы** | можно отправить ссылкой, переживают F5, работают «Назад» и «Вперёд» |
| Скважины, заявки, сообщения | **TanStack Query** | это данные сервера: загрузка, ошибки, кеш, обновление после изменений |
| Избранное, имя для комментариев, компактный вид | **Zustand** + localStorage | личные настройки этого браузера, нужны в разных компонентах |
| Текст в полях, открытое окно, перетаскиваемая карточка | **useState** | временное состояние одного экрана |

### TanStack Query: оптимистичное обновление на доске

Когда карточку перетаскивают в другую колонку:
1. `onMutate` — запросы отменяются, текущие данные запоминаются, карточка **сразу** переезжает в кеше.
2. Запрос `PATCH /api/tickets/:id` уходит на сервер.
3. `onError` — если сервер ответил ошибкой, данные возвращаются из сохранённой копии, и показывается сообщение.
4. `onSettled` — список заявок и карточка скважины перезагружаются, потому что у скважины могла измениться дата проверки.

Для пользователя доска реагирует мгновенно, но данные никогда не расходятся с сервером.

### Zustand

```ts
export const useFavoritesStore = create<FavoritesState>()(
  persist(
    (set) => ({
      ids: [],
      toggle: (id) => set((s) => ({ ids: s.ids.includes(id) ? s.ids.filter((x) => x !== id) : [...s.ids, id] })),
      clear: () => set({ ids: [] }),
    }),
    { name: 'svetofor-favorites', storage: createJSONStorage(() => localStorage), skipHydration: true },
  ),
)
```

- `persist` сохраняет состояние в `localStorage`.
- `skipHydration` нужен потому, что сервер не знает содержимого `localStorage`. Сначала страница
  рисуется как на сервере, а сохранённые данные подставляются после (`StoreHydrator`). Иначе
  React выдал бы ошибку несовпадения HTML.
- Компоненты подписываются на нужную часть: `useFavoritesStore((s) => s.ids)`. Перерисовываются
  они только при изменении этой части.

### Фильтры в адресе

`/wells?status=RED&ngdu=3&page=2`:
1. Серверный `page.tsx` читает параметры и проверяет их схемой Zod (`parseWellFilters`). Неверное
   значение не ломает страницу, а заменяется значением по умолчанию.
2. Экран получает готовые фильтры через props.
3. При смене фильтра `router.replace` меняет адрес, и страница получает новые фильтры.
4. Поиск срабатывает, когда пользователь перестал печатать (`useDebouncedCallback`, 350 мс),
   а не на каждую букву.

### Серверные и клиентские компоненты

- `page.tsx` и `layout.tsx` — **серверные**: читают параметры адреса, cookie и данные.
- `"use client"` стоит только на интерактивных экранах.
- Главная получает сводку из API **на сервере** и приходит в браузер уже с цифрами.
- Админка проверяет вход **на сервере**: `layout` спрашивает `/api/auth/me` с cookie пользователя
  и без входа перенаправляет на страницу входа.

### Формы

Одна схема Zod — две проверки:
1. в браузере — сразу, без запроса на сервер;
2. на сервере — повторно, потому что клиенту доверять нельзя.

Ошибки сервера по полям (например, «Этот номер уже занят») приводятся к тому же виду и появляются
под нужным полем. Поля формы связаны с подписями (`htmlFor`), ошибки — с полями (`aria-describedby`).

### Модальные окна

Сделаны на встроенном элементе `<dialog>`: браузер сам закрывает окно по Esc, держит фокус
внутри и затемняет фон. Форма внутри монтируется заново при каждом открытии, поэтому поля всегда чистые.

## 5. Демонстрация (по шагам)

1. `npm run setup`, затем `npm run dev`, открыть http://localhost:3000.
2. **Главная:** блок «Светофор сейчас» с живыми цифрами из базы.
3. **Скважины:** нажать «Срочно проверить» (адрес станет `?status=RED`), поискать по номеру, отметить ★,
   включить «Избранные». Обновить страницу: избранное и фильтры на месте.
4. Открыть красную скважину, нажать **«Создать заявку»**, отправить пустую форму (появятся ошибки), заполнить и создать.
5. **Доска:** перетащить новую заявку в «В работе», затем в «Проверено». Вернуться к скважине:
   «Последняя проверка — сегодня».
6. Открыть заявку, добавить комментарий, обновить страницу: имя подставилось само.
7. **Контакты:** отправить сообщение.
8. **Админ-панель:** открыть `/admin` без входа — произойдёт перенаправление на вход. Ввести неверный
   пароль, потом верный. Добавить скважину с отклонением 30% (предпросмотр покажет «Срочно проверить»),
   поменять на 5% (станет зелёной), удалить. Прочитать и удалить сообщение. Выйти.
9. В DevTools → Application → Cookies: у `svetofor_admin` стоит флаг **HttpOnly**.
10. `npm test` — 26 тестов бэкенда проходят.

## 6. Вопросы и ответы

**Зачем отдельный бэкенд, если в Next.js есть свои API-маршруты?**
Так требует задание, и это правильнее для роста проекта: бизнес-логика, база и права доступа
собраны в одном сервисе. С ним смогут работать и другие клиенты, например мобильное приложение.

**Что такое JWT и почему он в cookie, а не в localStorage?**
JWT — подписанный сервером «пропуск» с id и логином администратора. Подделать его без секретного
ключа нельзя. В `localStorage` токен может украсть любой вредоносный скрипт на странице, а
httpOnly-cookie JavaScript прочитать не может.

**Если cookie подделать, пустит ли в админку?**
Нет. `proxy.ts` видит, что cookie есть, и пропускает дальше, но `layout` админки спрашивает API,
а `AdminGuard` проверяет подпись токена и отвечает 401. Это проверено.

**Зачем тогда `proxy.ts`?**
Это быстрая проверка для удобства: человек без cookie сразу попадает на страницу входа, и
страница не начинает рисоваться зря. Права он не проверяет.

**Почему Zustand и TanStack Query, а не Redux?**
Это разные виды состояния. Данные сервера требуют кеша, повторных запросов и синхронизации — это
делает TanStack Query. Состояние интерфейса (избранное, настройки) простое — для него достаточно
Zustand, без лишнего шаблонного кода Redux.

**Что такое оптимистичное обновление?**
Интерфейс меняется сразу, не дожидаясь ответа сервера. Если сервер ответит ошибкой, изменение
откатывается. Так работает перетаскивание на доске.

**Что будет, если два человека одновременно двигают одну заявку?**
Последнее изменение сохранится, а после каждого изменения доска перезагружает данные с сервера.
Для полной защиты можно добавить проверку версии записи (оптимистичную блокировку).

**Зачем проверять данные на сервере, если их проверил браузер?**
Запрос можно отправить в обход формы — через DevTools или curl. Сервер — последняя линия защиты.

**Как хранится пароль?**
Хранится хеш scrypt с солью вида `scrypt$соль$хеш`. Scrypt специально медленный, поэтому подбор
занимает очень много времени. Соль делает хеши одинаковых паролей разными.

**Что такое миграция?**
Файл с SQL-изменениями структуры базы. Миграции хранятся в Git, поэтому у всех разработчиков
структура базы одинаковая и воспроизводится одной командой.

**Почему статус скважины нельзя выставить вручную?**
Это правило системы «Светофор»: цвет определяется измерением, а не мнением человека. Поэтому статус
рассчитывается на сервере функцией `statusFromDeviation`.

**Как тестировался проект?**
26 автотестов бэкенда (правила, безопасность, проверка данных). Интерфейс проверен в браузере:
фильтры, избранное, перетаскивание, откат при ошибке сервера, формы, вход, админка, мобильная вёрстка.

**Что бы вы улучшили?**
PostgreSQL вместо SQLite; несколько ролей (инженер, диспетчер, администратор); история изменений
заявки; уведомления о новых красных скважинах; e2e-тесты интерфейса на Playwright.

## 7. Итог

- **Бэкенд:** NestJS, 6 модулей, Prisma + SQLite, миграции и начальные данные, JWT, 26 тестов.
- **Фронтенд:** Next.js 16 + React 19, 8 разделов, слоистая архитектура.
- **Состояние:** TanStack Query (данные сервера, оптимистичные обновления), Zustand (избранное, настройки), адрес страницы (фильтры).
- **Zod:** формы, ответы API, параметры адреса — на обеих сторонах.
- **Админ-панель:** вход, управление скважинами, заявками и сообщениями; права проверяет сервер.
