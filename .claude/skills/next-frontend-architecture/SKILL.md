# Архитектура фронтенда

Применяй этот скилл к проектам на Next.js App Router, React и TypeScript. Сначала проверь структуру проекта и документацию установленной версии Next.js. Не переноси правила Next.js в проекты на другом фреймворке.

## Структура

- src/app/ — маршруты, page.tsx, layout.tsx, чтение параметров URL и данных запроса на сервере. Страница собирает экран из компонентов; не хранит большую бизнес-логику.
- src/components/<feature>/ — экраны и визуальные части конкретной функции.
- src/flows/ — хуки, собирающие данные, действия и состояние для одного экрана или пользовательского сценария.
- src/interactions/ — TanStack Query: ключи запросов, загрузка данных, мутации, polling и обновление кеша.
- src/layers/use-cases/<feature>/ — действия приложения и правила, которые должны работать независимо от React и React Query.
- src/layers/infrastructure/<feature>/ — HTTP-клиенты, сериализация запросов, обработка ответов и интеграции с внешними сервисами.
- src/layers/domain/<feature>/ — типы, схемы валидации и правила предметной области. Этот слой не зависит от UI и транспорта.
- src/common/ — действительно общие UI-элементы, провайдеры и утилиты без логики конкретной функции.
- src/assets/ — стили и исходные ресурсы.

## Направление работы

Типичный путь вызова: app → component → flow → interaction → use-case → infrastructure → API.

Это схема движения вызова, а не требование создать семь файлов для каждой функции. domain может использоваться несколькими слоями, но сам не импортирует UI, React Query или API-клиент. common не зависит от конкретной функции.

Создавай слой только тогда, когда у него есть своя ответственность:

- Статической странице могут хватить app и components.
- Простому запросу могут хватить API-клиента и interaction.
- use-case нужен, когда есть правило, преобразование или последовательность действий; не создавай функцию, которая лишь переименовывает один вызов API.
- flow нужен, когда экран объединяет несколько запросов, мутаций или состояний; не выноси в него каждый отдельный useState.

## Сервер и браузер

Оставляй page.tsx и layout.tsx серверными компонентами, когда им не нужны обработчики событий и браузерные API. На сервере читай параметры маршрута, cookie и данные, зависящие от запроса. Передавай клиентскому экрану необходимые сериализуемые значения через props.

Добавляй "use client" на границе интерактивного UI: формы, события, useState, useEffect, React Query и браузерные API. Не помечай весь маршрут клиентским только потому, что один его элемент интерактивен.

Разделяй состояние по назначению:

- URL — фильтры и параметры, которые должны переживать обновление страницы или копирование ссылки.
- TanStack Query — данные сервера, загрузка, ошибки и кеш.
- Локальный React state — временное состояние интерфейса, например открытый диалог или несохранённый ввод.

## API и безопасность

Сосредоточь fetch, базовый URL, credentials, обновление сессии и общую обработку ошибок в инфраструктурном слое. Не повторяй эту логику в компонентах.

Считай ответ внешнего API неизвестными данными и проверяй его на границе API-клиента, например схемой Zod. Если формат API отличается от модели приложения, преобразуй его в инфраструктурном слое.

Проверка маршрута через proxy.ts может перенаправить пользователя на вход. Права доступа к данным всегда проверяет сервер или backend; наличие cookie само по себе не подтверждает полномочия.

## Добавление функции

1. Определи URL и входные параметры страницы.
2. Определи модель данных и контракт API.
3. Реализуй доступ к API в infrastructure.
4. Добавь use-case, если есть правила приложения.
5. Добавь query или mutation с понятным ключом кеша и точечным обновлением после изменений.
6. При необходимости собери запросы и действия в flow.
7. Сделай экран в components/<feature>; покажи состояния загрузки, ошибки и пустого результата.
8. Подключи экран в app/<route>/page.tsx.

Сохраняй названия по предметной области проекта. Не создавай универсальные папки и абстракции без реального повторного использования.
