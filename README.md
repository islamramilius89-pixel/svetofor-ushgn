# 🚦 Светофор УШГН

Веб-приложение для мониторинга нефтяных скважин. Система «Светофор» анализирует ток двигателя
насоса (УШГН — установка скважинного штангового глубинного насоса) и подсвечивает скважины:
🟢 норма, 🟡 отклонение, 🔴 срочно проверить. По проблемным скважинам инженеры ведут заявки
на доске в стиле Jira.

## Возможности

| Раздел | Что можно делать |
|---|---|
| **Главная** `/` | живая сводка из базы (сколько скважин каждого цвета, открытые заявки) и результаты опытной эксплуатации |
| **Скважины** `/wells` | поиск по номеру, фильтры по статусу и НГДУ, сортировка, пагинация, ★ избранное; фильтры хранятся в адресе |
| **Карточка скважины** `/wells/:id` | отклонение тока, дата последней проверки, заявки по скважине, создание заявки |
| **Доска заявок** `/board` | колонки «Новые → В работе → Проверено», перетаскивание карточек (и кнопки ← → для клавиатуры и телефона), поиск, фильтр по приоритету, компактный вид, создание заявки |
| **Заявка** `/tickets/:id` | смена статуса, приоритета и исполнителя, комментарии (имя запоминается) |
| **Контакты** `/contact` | форма обратной связи |
| **Админ-панель** `/admin` | вход по логину и паролю; сводка; добавление, изменение и удаление скважин; удаление заявок; чтение и удаление сообщений |

**Главное правило предметной области:** статус скважины не выставляется вручную, он рассчитывается
из отклонения тока: до 10% — 🟢, 10–25% — 🟡, от 25% — 🔴. Когда заявку переводят в «Проверено»,
у скважины обновляется дата последней проверки.

## Стек

| Часть | Технологии |
|---|---|
| Фронтенд | **Next.js 16** (App Router), **React 19**, **TypeScript**, **Tailwind CSS 4** |
| Состояние | **TanStack Query** — данные сервера; **Zustand** — избранное и настройки интерфейса |
| Проверка данных | **Zod** — формы, ответы API, параметры адреса (и на фронтенде, и на бэкенде) |
| Бэкенд | **NestJS 12**, **Prisma 7**, **SQLite**, JWT в httpOnly-cookie |
| Тесты | **Vitest** + Supertest (26 тестов бэкенда) |

## Запуск

Нужен Node.js 22 или новее.

```bash
npm run setup   # зависимости фронтенда и бэкенда + база данных с тестовыми данными
npm run dev     # бэкенд (порт 4000) и фронтенд (порт 3000) одной командой
```

Откройте http://localhost:3000.

**Вход в админ-панель (данные для разработки из `backend/prisma/seed.ts`):** логин `admin`, пароль `svetofor-admin`.
Задать свои можно переменными `ADMIN_LOGIN` и `ADMIN_PASSWORD` перед `npm --prefix backend run db:seed`.

| Команда | Что делает |
|---|---|
| `npm run dev` | фронтенд и бэкенд в режиме разработки |
| `npm test` | тесты бэкенда (модульные и API) |
| `npm run lint` | ESLint фронтенда |
| `npm run build` | production-сборка фронтенда с проверкой типов |
| `npm --prefix backend run db:seed` | вернуть базу к начальным данным |
| `npm --prefix backend run db:migrate` | создать миграцию после изменения `schema.prisma` |

Переменные окружения (необязательные): `API_URL` — адрес бэкенда для фронтенда (по умолчанию
`http://localhost:4000`); `DATABASE_URL`, `JWT_SECRET`, `PORT` — для бэкенда. В production
`JWT_SECRET` обязателен: без него сервер не запустится.

## Архитектура

```
Браузер ──► Next.js (порт 3000) ──/api/*──► NestJS (порт 4000) ──► Prisma ──► SQLite
             серверные компоненты             контроллеры → сервисы
             + клиентские экраны              guard, проверка Zod
```

Браузер обращается только к Next.js: запросы `/api/*` Next.js пересылает на NestJS (`rewrites` в
`next.config.ts`). Поэтому cookie администратора работает на одном домене, и CORS не нужен.

### Фронтенд (`src/`)

Устроен по скиллу [`next-frontend-architecture`](.claude/skills/next-frontend-architecture/SKILL.md).
Путь вызова: `app → components → flows → interactions → use-cases → infrastructure → API`.

```
src/
├── app/                    маршруты; page.tsx читают параметры адреса на сервере
│   ├── admin/(panel)/      страницы админки; layout проверяет вход через API
│   └── admin/login/        вход
├── proxy.ts                быстрый редирект в /admin/login, если нет cookie
├── components/<feature>/   экраны: home, wells, board, tickets, contact, admin, layout
├── flows/                  сценарии экранов: use-wells-flow, use-board-flow, use-ticket-flow…
├── interactions/           TanStack Query: ключи, запросы, мутации, оптимистичные обновления
├── stores/                 Zustand: избранное, настройки (сохраняются в localStorage)
├── layers/
│   ├── domain/             типы, схемы Zod, правила (статус по отклонению, колонки доски, фильтры)
│   ├── use-cases/          отправка форм: проверка → запрос → ошибки по полям
│   └── infrastructure/     HTTP-клиент (браузер и сервер), клиенты API
└── common/                 Button, Dialog, поля форм, состояния загрузки, провайдеры
```

| Где хранится состояние | Что там |
|---|---|
| **Адрес страницы** | фильтры скважин и доски (можно отправить ссылкой, переживают F5) |
| **TanStack Query** | всё, что пришло с сервера: скважины, заявки, сообщения |
| **Zustand** | избранные скважины, имя для комментариев, компактный вид доски |
| **useState** | введённый в форму текст, открытое модальное окно, перетаскиваемая карточка |

### Бэкенд (`backend/`)

```
backend/
├── prisma/
│   ├── schema.prisma       модели: Ngdu, Well, Ticket, Comment, Message, Admin
│   ├── migrations/         миграции базы
│   └── seed.ts             тестовые данные: 6 НГДУ, 60 скважин, 14 заявок, администратор
├── src/
│   ├── auth/               вход, JWT, AdminGuard, хеширование пароля (scrypt), защита от подбора
│   ├── wells/              скважины и НГДУ; правило статуса — well-status.ts
│   ├── tickets/            заявки и комментарии; правило закрытия — ticket-rules.ts
│   ├── messages/           форма обратной связи
│   ├── stats/              сводка
│   └── common/             проверка Zod (pipe), единый формат ошибок (filter)
└── test/                   тесты API
```

### API

Все ошибки приходят в одном формате: `{ "error": "текст", "fieldErrors": { "поле": "текст" } }`.

| Метод | Адрес | Доступ | Что делает |
|---|---|---|---|
| GET | `/api/stats` | все | сводка по статусам |
| GET | `/api/ngdus` | все | список НГДУ |
| GET | `/api/wells?search&ngduId&status&ids&sort&page&pageSize` | все | список скважин |
| GET | `/api/wells/:id` | все | скважина с заявками |
| POST, PATCH, DELETE | `/api/wells`, `/api/wells/:id` | 🔒 админ | управление скважинами |
| GET | `/api/tickets?search&priority&wellId` | все | список заявок |
| GET | `/api/tickets/:id` | все | заявка с комментариями |
| POST, PATCH | `/api/tickets`, `/api/tickets/:id` | все | создание и изменение заявки |
| DELETE | `/api/tickets/:id` | 🔒 админ | удаление заявки |
| POST | `/api/tickets/:id/comments` | все | комментарий |
| POST | `/api/messages` | все | отправить сообщение |
| GET, DELETE | `/api/messages`, `/api/messages/:id` | 🔒 админ | чтение и удаление сообщений |
| POST | `/api/auth/login`, `/api/auth/logout` | все | вход и выход |
| GET | `/api/auth/me` | 🔒 админ | текущий администратор |

## Безопасность

- Пароль хранится только в виде хеша **scrypt** с солью.
- Токен входа лежит в **httpOnly-cookie**: JavaScript на странице его не прочитает.
- Права проверяет **сервер** (`AdminGuard`) на каждом запросе. `proxy.ts` и проверка в `layout`
  админки нужны для удобства (редирект на вход), а не для защиты данных.
- После 5 неудачных попыток вход для логина блокируется на 15 минут.
- Email из формы обратной связи видит только администратор.
- Все входные данные проверяются схемами Zod на сервере, даже если их уже проверил браузер.

## Ограничения

- Блокировка попыток входа хранится в памяти сервера и сбрасывается при его перезапуске.
- SQLite подходит для демонстрации; для нескольких серверов нужен PostgreSQL (в Prisma это смена провайдера).
- `npm audit` показывает уязвимости в инструментах разработки (`eslint-config-next`, CLI Prisma).
  В работающее приложение эти пакеты не попадают.
